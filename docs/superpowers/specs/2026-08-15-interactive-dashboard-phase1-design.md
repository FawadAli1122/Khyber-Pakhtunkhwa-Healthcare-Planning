# KP Healthcare Plan — Interactive Dashboard (Phase 1)

Status: Approved design, pre-implementation
Date: 2026-08-15

## 1. Purpose

Turn `report/KP_Healthcare_Plan.html` — currently a static, generated document
with matplotlib PNGs baked in as base64 — into an interactive dashboard:
sortable/filterable district data, a clickable choropleth map, and a new
methodology section that places this project's approach against the
international GIS-based health-planning toolkit (2SFCA, WHO AccessMod, WHO
SARA, location-allocation siting models).

This is phase 1 of a larger roadmap (§7). It intentionally does **not**
include the AI providers, admin panel, document ingestion, or the
2SFCA/p-median algorithm upgrades — those are separate, later specs.

## 2. Context From Report Review (2026-08-15)

`report/KP_Healthcare_Plan.html` was audited before this design: 574KB,
828 lines, zero `<script>` tags (fully static), generated by
`scripts/14_build_html_report.py` from `data/processed/*.csv|json` and
`gis/*.shp`. No blank/missing content found — apparent `TBD`/`NaN` grep hits
were false positives (substring matches inside words like "financing") or
disclosed, legitimate data gaps (`n/a km` for districts with no mapped
facility, explained in the report's own disclaimer as a registry gap for
newly-merged tribal districts). Content is sound; the gap is purely that
it's non-interactive.

## 3. Approach

**Client-side interactive single file, generated by the pipeline.**
`scripts/14_build_html_report.py` is extended (kept as one script, not
split) to emit a dashboard-flavored HTML file: pipeline data is inlined as
JSON, and vanilla JS drives the interactivity. No build toolchain, no CDN
dependency, still a single file you open by double-click — consistent with
every other artifact this pipeline produces.

Rejected alternatives:
- **React/Vue SPA** — would add an npm/bundler toolchain to a project that
  is otherwise pure Python; no payoff at this phase's scope.
- **Serve it from a local backend now** — the payoff (secure key storage,
  admin panel) only exists once phase 2 (AI/admin) lands. Standing up a
  server today means maintaining two serving paths in parallel for nothing;
  phase 2's backend will wrap this same generated file as its frontend.

## 4. Data Layer

Source of truth stays `data/processed/district_metrics.csv` (35 rows: area,
population, density, elevation/slope, institutions, facility count,
beds/doctors per 1,000, accessibility km, terrain difficulty, gap score,
need tier, and the 2029/2031/2046 horizon projections) joined with district
polygon geometry from `data/processed/boundaries.json`.

The build script serializes both into one `<script type="application/json"
id="dashboard-data">` block embedded in the HTML (not a separate `.json`
fetched at runtime — `file://` pages can't `fetch()` a sibling file without
tripping CORS, and inlining preserves the zero-dependency, double-click-to-
open property). Boundary polygons are simplified (Douglas-Peucker, coarse
tolerance) before embedding to keep the coordinate payload small, since the
dashboard only needs recognizable district shapes, not survey precision.

## 5. Interactive Components

- **District table** — replaces the current static table under
  `#district-data`. Sortable by any numeric/text column, free-text search
  box (district/division name), tier filter chips (Critical/High/
  Moderate/Low — reusing the existing tier colors), row click expands a
  detail panel with the full metric set including the horizon projections.
- **Choropleth map** — inline SVG rendered client-side from the embedded
  boundary geometries, filled by gap-score tier using the report's existing
  `TIER_COLORS`. No tile server or basemap — offline-safe. Clicking a
  district highlights/scrolls to its table row; the table's active filter
  also dims non-matching districts on the map, so the two views stay in
  sync.
- **Charts** — the current static matplotlib PNGs (facility distribution,
  gap-score distribution, etc.) are rebuilt as inline SVG/small JS so they
  can respond to the same tier filter as the table/map. Chart specs,
  palette, and mark choices follow the dataviz skill at implementation
  time — not fixed in this design doc.
- **New "Methodology: International GIS Standards" section** — written
  content (not interactive) placed near the existing `#sources` section,
  covering:
  - **2SFCA / Enhanced 2SFCA** — spatial accessibility weighted by
    distance/capacity, contrasted with this report's current straight-line
    `accessibility_km` metric.
  - **WHO AccessMod** — travel-time accessibility modeling from DEM + roads
    + land cover; noted as the natural next step since the pipeline already
    fetches a DEM (`gis/KP_DEM.tif`) and OSM roads
    (`data/raw/osm_roads.json`) but doesn't yet route through them.
  - **WHO Service Availability & Readiness Assessment (SARA)** — the
    availability-vs-readiness framing, mapped onto this report's existing
    beds/doctors/institution-count metrics.
  - **Location-allocation siting (p-median / Maximal Covering Location
    Problem)** — the standard optimization approach for new-facility
    siting, contrasted with the current heuristic in
    `11_suggest_new_sites.py`.
  Each subsection states plainly what this project currently does and what
  adopting the fuller method would change — setting up phase 1b (§7)
  without implementing it here.

## 6. Testing / Verification

- `tests/verify_*.py` convention continues: add
  `tests/verify_dashboard.py` that renders the build script's output and
  checks (a) the embedded JSON block parses and row count matches
  `district_metrics.csv`, (b) every district in the metrics CSV has a
  matching boundary geometry, (c) no `TBD`/`NaN`/empty-cell regressions
  (reusing the grep checks run during this design's report audit).
  Renders the report and asserts sortable/filterable elements exist.
- Manual check: open the generated file directly in a browser (no server)
  to confirm it still works `file://`, since that's the whole point of the
  inlined-JSON approach.
- Visual/interaction check against the dataviz skill's palette validator
  once charts are implemented.

## 7. Roadmap (context for later phases — not this spec's scope)

Decided during brainstorming, recorded here so later specs don't re-litigate:

- **Phase 2 — Backend + admin panel.** A local server (Python
  FastAPI/Flask) serves the dashboard and holds AI provider API keys
  server-side (config/.env), never in client HTML/JS. Admin panel is a UI
  against this server, not an embedded secret.
- **Phase 3 — Multi-provider AI integration.** Claude, OpenAI, Gemini,
  Grok, and Groq wired in behind the phase-2 backend, selectable from the
  admin panel.
- **Phase 4 — Document ingestion.** Upload Excel/PDF/Word/HTML/database
  inputs; AI extracts data and updates plan content/data with full
  autonomy (per explicit user decision — no human-in-the-loop review
  gate), then the dashboard is regenerated.
- **Phase 1b — Methodology upgrade.** Replace `accessibility_km`'s
  straight-line distance with a 2SFCA-style network/travel-time metric
  using the already-fetched road network, and replace
  `11_suggest_new_sites.py`'s heuristic with a p-median/MCLP optimization.
  Deferred out of phase 1 because it changes the underlying numbers, not
  just how they're displayed — a bigger, separately-reviewable change.
